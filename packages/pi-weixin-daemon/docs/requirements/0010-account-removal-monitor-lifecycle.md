## Goal

用户希望明确区分“账号不再使用”和“磁盘文件已清理”，不因凭据或缓存删除失败而让账号重新运行。删除账号前必须先显式解除项目绑定，不能通过 logout 隐式修改项目关系。

同时简化每账号 monitor 的管理：一个管理者负责启动与停止，不让账号登记、transport、轮询任务各自维护重复的生命周期。

## Solution

用户先通过项目命令解绑，再在 daemon 在线时执行 `pi-wx logout <name>`。daemon 停止该账号接收任务，并将账号从持久化索引删除；索引保存成功即视为账号删除成功，随后尽力清理文件。

索引保存失败时报告错误、记录日志并重新启动该账号 monitor；文件清理失败则不恢复账号，只在日志列出残留文件路径，提示用户手动删除。daemon 重启依据索引决定启动账号，不因残留凭据重新登记或运行账号。

## User Stories

1. 作为维护者，我希望删除有项目绑定的账号时得到拒绝和解绑提示，避免误改项目配置。
2. 作为维护者，我希望多个微信账号独立接收消息，一个账号等待或重试不阻塞其他账号，也不额外启动线程或进程。
3. 作为维护者，我希望停止账号后，旧轮询或尚未完成的入站媒体处理不再分发新消息、写回缓存，避免删除后文件重新出现。
4. 作为维护者，我希望账号列表保存失败时删除明确失败，并恢复原 monitor，使一次失败的操作不会静默停掉账号。
5. 作为维护者，我希望账号删除成功后，即使文件清理失败，它也不再出现在登记列表或在 daemon 重启后运行；日志告诉我具体要手工清理什么。
6. 作为脚本调用者，我希望拒绝、停止失败、索引保存失败使用失败结果；删除已经提交后的文件清理警告不再被误报为账号删除失败。
7. 作为维护者，我希望同账号的绑定、启动、reload 与删除不会交叉执行，避免删除过程中又启动任务或留下新的绑定。

## Implementation Decisions

### 用户入口与绑定规则

- 沿用 CLI 仅接受唯一、区分大小写的 name，账号选择类 RPC 仅接受 ID 的边界；不恢复 ID/name 自动猜测。
- logout 必须由在线 daemon 执行。daemon 不可连接时直接失败，不再本地删除，即使之前 account.list 成功、随后 logout 建连失败也不降级。
- 删除前检查持久项目配置，启用和停用项目的绑定均阻止删除。错误提示指出关联项目及先解绑的操作。
- 有绑定时零副作用：不停止 monitor、不修改索引、不删除文件、不隐式解绑。
- 项目解绑保持现有命令及其重建项目 controller/会话的行为，本需求不增加“解绑不中断 Pi”的保证。

### monitor 生命周期所有权

- 由 AccountManager 统一拥有每账号的取消控制器与轮询任务；同账号最多一个活跃接收任务。任务完成回收不能误删后来启动的新任务。
- 保留每账号异步长轮询，不改为全局串行遍历；不引入额外线程、进程、消息队列、后台扫描或完整的新状态机。
- daemon 启动以及登录、reload、账号删除的受控变化点同步登记集合；不在每轮接收中扫描磁盘。
- 仍登记但无可用凭据的账号不启动 monitor；登记身份与运行状态分离。
- transport 保留微信收发、媒体、归一化与 gate 适配，不再重复拥有 controller/task 或独立的接收生命周期。通知开始/停止及 context-token restore 只由一处安排，避免重复执行。
- monitor 保留 getUpdates、接收进度、消息交付以及现有重试/退避/token 过期暂停行为；不借此改投递保证。仍在分发前保存接收进度。

### 停止接收

- 停止通过 AbortController 通知网络长轮询和重试等待退出，再等待轮询任务完成；不得吞掉真正的停止错误并假装停止成功。
- 请求返回后、保存接收进度前、每次交付前检查任务是否已取消；入站媒体下载返回后，在缓存写入及交付前同样检查旧接收任务是否仍有效。
- 停止完成后，旧接收任务不得继续发起下一轮请求、写入进度/context-token 或交付新消息。
- monitor 不等待整轮 Pi 处理完成，不为停止接收主动调用 Pi abort；现有 UI/权限交互依赖持续接收，不能因 await 完整消息处理而死锁。
- 已交付的业务工作不属于接收任务取消范围；账号删除后不保证其后续微信发送成功。

### 删除提交点与失败补偿

概念流程（不是已实现状态机）：

```text
同账号操作互斥
  检查绑定；有绑定则拒绝
  停止 monitor，并确认轮询退出
  原子保存从索引移除此账号后的列表
    保存失败：删除失败，记录错误，恢复原 monitor
    保存成功：账号删除已提交，进入尽力文件清理
结束同账号操作互斥
```

- `accounts.json` 仍是持久化账号登记的依据。保存删除后的列表是更新现有索引，不是另存一份账号列表。
- 以原子替换避免索引文件部分写入；保存失败应保留旧索引，尚未开始删除凭据和缓存。
- monitor 停止异常时不提交索引删除、不清理文件；操作返回失败并记录真实状态。
- 保存索引失败时返回失败、记录错误，并在原账号原本有 monitor 时尝试恢复；原本无 monitor 的登记账号不被无故启动。
- 恢复启动也失败时，必须同时暴露删除失败与恢复失败，保留登记记录并准确显示已停止/错误状态，不报告恢复成功。
- “原子”指持久索引修改具有明确提交点；网络任务无法与文件系统组成真正的跨资源事务，重新启动 monitor 是补偿操作。重启 daemon 时以已持久化索引恢复，避免把补偿称作绝对原子保证。
- 同账号绑定、启动、reload 与删除使用局部操作互斥；删除与清理期间不得重新启动或重新绑定。不同账号的长轮询仍独立运行，共享索引的更新不得覆盖其他账号的并发变更。

### 文件清理与反馈

- 仅在索引删除提交后清理该账号凭据及辅助缓存，不从文件删除成功与否推导账号是否仍登记。
- 文件不存在视为已清理；其他清理错误记录日志，指出残留文件的具体路径并提示用户手动删除。日志不包含 token、context-token 或凭据文件内容。
- 清理失败不回滚索引、不重启 monitor，也不将已提交的账号删除改成失败结果。不得声称所有凭据均已清理。
- 不新增清理命令、自动重试、垃圾回收扫描、待删除记录或 name 恢复存储。进程在提交后、清理前退出可能留下文件，但重启不得据此重新启动账号。

### 与现状、发布流程的关系

- 本需求替代 ADR-0007 的 logout 离线降级，以及 ADR-0009 的“文件清理失败保留登记供按名重试”顺序；保留 CLI/RPC name/ID 分界和登记列表合并运行状态的约定。
- 历史 ADR 保留原文；实施时新增关联 ADR 记录新决定，不覆写历史理由。
- 禁止离线 logout、有绑定拒绝删除和清理警告不等于删除失败均属于 BREAKING 用户行为变更；实施应更新 README/help、相关测试及 minor changeset，不手动改版。
- 本 spec 仅记录计划，不表示运行时代码已经采用上述流程。

## Testing Decisions

按用户要求保持测试简单，只覆盖核心行为，不为边缘情况建立复杂测试体系。

- 优先复用现有临时目录、本地 CLI/RPC 集成测试及 fake transport/runtime，不重复逐层 mock。
- 在现有 monitor 测试中补一条基本取消测试，确认停止后轮询退出；不穷举取消时机。
- 全部离线，不操作真实账号、凭据、微信接口或模型。

核心场景：

1. 有项目绑定时拒绝删除，不产生副作用。
2. daemon 离线时拒绝删除，不执行本地清理。
3. 无绑定账号正常删除：monitor 停止、索引移除、文件清理，重启后不再启动。
4. 模拟一次索引保存失败：操作报错、保留账号及文件、恢复 monitor。
5. 模拟一次文件清理失败：账号删除仍成功，日志提示残留路径和手动清理。

不新增故障码/文件类型全组合、复杂并发交错、崩溃恢复或恢复再次失败的专项测试；不搭建新的测试框架。实现仍须遵守上述行为约定，已有无关回归测试保留。

每阶段代码变更先使用根 Biome 格式化，再运行受影响包类型检查和相关测试；最终跑全包离线测试和构建，进行独立审查。

## Out of Scope

- 当前创建 spec 的操作不修改运行时代码，不安装、重启或操作用户真实 daemon。
- 不改变项目解绑导致会话重建的既有行为，不实现持续 Pi 回合的无缝解绑。
- 不引入账号数据库、分布式事务、全局串行轮询、完整生命周期状态机或后台文件清理服务。
- 不把 name 移入索引、不增加账号数据迁移，也不通过删除顺序之外的事务日志保存恢复身份。
- 不改变微信协议、长轮询重试策略、RPC framing、广播超时或已有 Pi SDK 边界。
- 不承诺清理失败后敏感文件已消失，也不承诺进程崩溃后自动补做文件清理。

## Further Notes

- 用户已确认：有绑定先解绑；禁止离线删除；同账号操作互斥；保留解绑行为；索引保存失败报错并恢复 monitor；清理失败只记录路径供手动删除。
- 用户已接受持久索引原子更新与 monitor 补偿的区别，以及恢复启动失败必须明确报告的边界。
- 用户要求测试保持简单，不覆盖复杂边缘情况；仅保留核心删除流程、两类关键失败反馈和基本轮询取消验证。
- 实施前需核对账号登记的所有写入入口，确保并发登录不会绕过索引更新与同账号互斥；若实现需要改变登录协议、离线登录行为或增加跨进程协调，应先澄清范围，不凭此 spec 扩大改造。
- 若实施发现阻塞问题则暂停；独立非阻塞问题另建 issue，不顺手扩大本需求。
