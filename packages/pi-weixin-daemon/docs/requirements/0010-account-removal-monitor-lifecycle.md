## Goal

用户希望控制面职责清晰：CLI 维护“应该运行什么”，daemon 维护“实际运行什么”。账号、项目、绑定关系的持久修改只有一个角色负责，不再混用 CLI 直接写文件和 daemon RPC 写文件。

账号删除前必须先显式解绑；登记删除、运行停止、文件清理分别反馈，不因为文件残留而恢复已删除账号。同时简化 monitor 的生命周期管理，不引入额外线程、队列或复杂状态机。

## Solution

CLI 统一维护项目配置、账号登记和凭据。修改时取得控制协调锁，重新读取并校验最新数据，原子保存后释放锁，再通知 daemon 读取当前配置并同步运行态。daemon 可以参与协调，但不写这些控制配置。

允许 daemon 离线时保存配置，下一次启动时应用。在线应用失败或结果未知时不回滚已保存配置，而是明确提示运行状态未同步。删除账号后，只有确认 monitor 已停止、且清理前再次确认账号未重新登记，才清理凭据和缓存；无法确认安全时保留文件，日志提示手动处理。

## User Stories

1. 作为维护者，我希望通过 CLI 管理账号、项目、绑定和启停配置，不必关心在线与离线时不同的文件写入路径。
2. 作为维护者，我希望删除有任何项目绑定的账号时直接被拒绝，先明确解绑，避免 logout 隐式修改项目关系。
3. 作为脚本调用者，我希望区分配置保存失败、保存成功但应用失败、应用成功但清理警告，避免把部分完成误认为全部成功或全部撤销。
4. 作为维护者，我希望多个账号独立长轮询，一个账号等待或重试不阻塞其他账号，管理命令可以串行以降低复杂度。
5. 作为维护者，我希望停止确认后旧接收任务不再写缓存或交付消息，清理也不会误删重新登录账号的新文件。
6. 作为维护者，我希望清理失败只留下明确的文件路径和人工操作提示，不自动恢复账号或增加后台清理系统。
7. 作为维护者，我希望同 ID 的凭据更新能在同步后实际生效，同用户账号替换也遵守先解绑的规则。

## Implementation Decisions

### 控制配置与运行数据的所有权

| 数据或操作 | CLI | daemon |
| --- | --- | --- |
| 账号登记 `accounts.json`、账号凭据 | 唯一写入角色；登录、替换、删除 | 只读，用于同步账号运行集合 |
| 项目 `config.json` | 唯一写入角色；创建、删除、绑定、解绑、enabled | 只读，用于同步项目运行实例和路由 |
| monitor、项目 controller、Pi 会话 | 请求同步或纯运行操作 | 管理实际运行生命周期与状态 |
| 接收进度、context-token、日志、会话与媒体文件 | 账号删除后的受控清理 | 运行期间读写 |

- “CLI 唯一写入”包含全部 CLI 进程，不代表天然没有并发；共同协调机制覆盖所有控制配置修改。
- 项目启用/停用修改持久 enabled；项目 restart 等不修改配置的运行操作仍通过 RPC 请求 daemon 执行。
- 项目 cwd 继续创建后固定，不开放修改 cwd 的新功能；同名项目删除重建可能合并为一次同步，因此复用实例时也比较 cwd，变化则重建。解绑继续采用现有 controller/会话重建行为。
- daemon 不再通过创建项目、绑定、logout 等 RPC 写入控制配置，也不能在启动时执行会写凭据/索引的隐式迁移；现有必要兼容迁移移到受控 CLI 写入入口，不借此新建账号格式迁移。
- 保留 CLI 账号参数 name-only、内部标识为 accountId。配置变更的 name 解析以锁内最新磁盘登记/凭据为准，不以可能滞后的 daemon 列表覆盖配置。
- 控制配置读取失败或损坏应明确失败，不能当空配置覆盖写入或据此停止全部账号。合法的初始空配置仍按首次使用处理。

### 写入与运行同步的协调

- 使用一把跨进程控制协调锁：CLI 的配置读—校验—写入及最终文件清理持有它；daemon 的读取快照至完成 reconcile 也参与同一协调。
- CLI 在锁内重新读取账号和项目配置，完成名称/用户冲突、账号登记及全部持久绑定检查，再提交修改。原子替换防止单个文件部分写入；互斥防止不同命令互相覆盖，不宣称多个文件共同原子提交。
- 有绑定就拒绝删除，包含 disabled 项目；拒绝时不修改登记、文件或 monitor，也不自动解绑。绑定先提交则删除拒绝，删除先提交则绑定因账号不再登记而拒绝。
- CLI 提交后必须释放控制锁，再通知 daemon 并等待；不得持锁等待需要获取该锁的 daemon，避免死锁。
- daemon 的启动、reload、项目 restart、关闭等生命周期操作通过一个进程内串行入口协调。不能先在锁外读取旧快照，之后再拿旧快照启动账号。
- 接受管理操作串行以及慢 reconcile 暂时阻塞其他管理命令；不串行各账号长期轮询，不在锁内等待扫码或整轮 Pi 工作。
- 锁等待应有明确失败/等待反馈，进程退出后不得留下永久占用。具体锁工具和数据结构属于实现选择，不增加事务系统或持久操作队列。
- 同一配置/数据实例只允许运行一个 daemon，单实例保护覆盖初始化至退出；socket 不存在或连接被拒绝不等于已经证明没有运行中的 monitor。
- CLI 通知必须对应相同配置/数据实例，不能把另一实例的响应当作已同步确认。

### 配置应用与结果语义

概念流程（不是持久状态机）：

```text
CLI：取得控制锁 → 读取并校验 → 保存配置 → 释放锁
  保存失败：报错，结束；不发起运行态修改或文件清理
  保存成功：通知 daemon 读取当前配置
    已确认离线：报告已保存，待下次启动应用
    在线应用成功：报告已保存、已应用
    应用失败或未知：非零退出，明确已保存、不回滚
```

- 通知只表示“读取当前期望配置”，不携带旧快照反复覆盖运行态；CLI 保存后退出、通知失败或超时，不自动回滚或盲目重试。
- 后续通知、人工 reload 或 daemon 重启可以重新同步；首版不增加文件监听、后台扫描或可靠通知队列。
- 并发配置变更可能替代尚未应用的前一次变更；应用结果应说明实际应用状态和错误，不能无条件宣称每个中间修改都已执行。
- reconcile 返回成功必须代表相关运行变更已完成；项目启动错误或 monitor 停止错误即使写入日志，也不能被伪装成整体应用成功。
- 离线提交配置允许成功返回“待下次启动”。无法确认离线、在线同步超时或失败时，非零退出并说明配置已经保存、应用结果未知；不把连接错误直接等同于无 daemon。
- 列表与状态输出区分持久登记/项目配置和实际 monitor/controller 状态，不因登记已删除就假装可能残留的旧任务已经停止。
- 取消原 spec 的“先停止后由 daemon 写索引、索引失败恢复 monitor”方案：CLI 保存失败时尚未通知改变运行态，不需要为这次保存操作补偿重启；保存后运行失败也不恢复已删除的登记。

### 登录、替换与凭据变更

- 扫码仍由 CLI 完成，等待扫码不占控制锁；提交时在锁内重新校验 name、userId 及替换涉及的全部账号绑定。
- 同用户登录将替换旧账号时，旧账号有持久绑定则拒绝本地替换，提示先解绑；无绑定才提交新的登记集合，并按相同停止确认和清理规则处理旧账号。
- 凭据先原子保存，再提交登记；中途失败可能留下未登记凭据，不把它自动视为登记成功，不承诺凭据和索引共同原子提交。
- 已有相同 ID 的有效凭据变化也需要 reconcile：先停止旧实例，再使用新凭据启动，不能因为 ID 已存在就跳过。凭据不写日志。
- 本地拒绝保存不表示能够撤销已经发生的微信扫码登录；本需求不承诺远端登录事务回滚。

### monitor 的轻量生命周期

- 由 AccountManager 统一拥有每账号的取消控制器与轮询 task；同账号最多一个活跃接收任务。旧任务完成回收不能误删后启动的任务。
- 保留每账号异步长轮询，不改成全局串行轮询；transport 保留收发、媒体、归一化及 gate 适配，不重复持有接收生命周期。
- 开始/停止通知和 context-token restore 在单一入口安排，避免重复。仍登记但无可用凭据的账号不启动 monitor，登记身份与运行状态分离。
- 保留接收进度、重试/退避、token 过期暂停及先保存进度再交付消息的既有语义，不顺手改变消息投递保证。
- 停止通过 AbortController 取消网络长轮询和重试等待，再确认轮询退出。停止失败不报告停止成功，也不启动同 ID 的第二个 monitor。
- 请求返回后、保存进度前、每次交付前以及入站媒体下载返回后，检查旧任务有效性；确认停止后不得再由旧接收路径写缓存或交付新消息。
- 停止不等待整轮 Pi 工作、不主动调用 Pi abort；持续接收仍用于 UI/权限回复。已交付的业务工作不属于接收取消范围，账号删除后不保证其后续发送成功。
- 本地接收停止与远端 notifyStop 分开：本地已经安全停止后，远端通知失败只是警告，不伪装成本地仍在接收。

### 删除与文件清理

```text
CLI 锁内检查所有绑定 → 从登记索引删除 → 释放锁
通知 daemon 同步 → 确认目标 monitor 已停止
CLI 重新取得控制锁 → 检查同 ID 仍未登记且停止确认仍有效
  安全：尽力清理凭据和缓存
  已重新登记或无法确认安全：跳过清理
```

- 删除登记是持久配置提交点，不等于旧 monitor 已停止；两者之间允许暂时滞后，反馈必须明确。
- 停止失败或未确认时不清文件、不回滚登记，提示应用未完成及后续 reload/重启。确认离线但无法取得可信的无运行任务保证时，也保留残留文件，不因 socket 错误猜测安全。
- 删除后取得停止确认也不能授权稍后无条件清理：清理前重新锁定、检查同 ID 是否再登记，避免删除新账号文件；若停止确认已不再适用，保守跳过，不增加代际事务机制。
- daemon 停止被移除账号时清除相关内存运行缓存，CLI 负责磁盘残留；同 ID 重新登录不得继承旧 owner 的无效 context-token。运行缓存清除不改变控制配置只读职责。
- 文件清理逐文件尽力执行；不存在视为已清理，其他失败记录具体残留路径并提示手动删除，不输出 token、context-token 或凭据内容。
- 仅文件清理警告不改变配置删除及应用成功结果，不恢复账号，不宣称凭据已全部消失。对停止未确认的情况，须说明先停止相关运行任务再手工清理，不能只提示删除文件。
- 不新增清理命令、待删除状态、恢复身份存储、后台清理或自动重试。CLI 在提交后退出可留下残留，后续启动只按登记索引恢复，不因孤儿凭据自动复活账号。

### 与现状、发布流程的关系

- 本需求调整 daemon 作为项目配置唯一 writer 的旧边界；项目和账号控制文件统一由 CLI 写入，业务运行和 Pi SDK 分层仍保留。
- 替代 ADR-0007 的在线账号列表选择权威及 daemon logout 写入/离线降级分叉；保留 name-only 输入、内部 ID 和 RPC 分帧。
- 替代 ADR-0009 的先清文件后注销索引顺序，保留登记与 monitor 状态区分；文件残留不再要求恢复 name 后重新 logout。
- 实施时新增关联 ADR，历史决定保留原文；迁移全部配置写入口，包含登录去重、daemon 启动迁移和项目修改 RPC，不能留下第二个 writer。
- 属于 BREAKING 控制面与用户行为变更，更新 README/help、相关测试和 minor changeset；不手动改版，不引入新的账号存储格式。
- 已按此职责划分完成实现；版本由 minor changeset 随发布流程生成。

## Testing Decisions

按用户要求保持测试简单，只覆盖核心行为，优先复用临时目录、本地 CLI/RPC 集成测试及 fake transport/runtime；全部离线，不操作真实凭据、微信或模型。

核心场景：

1. 有项目绑定拒绝删除且无副作用；先解绑后正常保存、同步停止和清理，重启不恢复已删账号。
2. 代表性配置保存失败保留原配置，不提前停止 monitor 或删除文件；离线保存则明确报告待应用。
3. 代表性同步/停止失败：明确配置已保存，非零退出、不清文件；代表性清理失败：已应用仍成功，日志给出手动处理路径。
4. 用最小可控交错验证共同协调规则：旧快照不能复活账号，清理不会误删已经重新登记的账号；不穷举所有并发顺序。
5. 同 ID 凭据更新能重建对应 monitor；基本取消测试确认接收退出且不等待 Pi，不逐项穷举取消时机。

不新增故障码/文件类型全组合、复杂崩溃恢复或多重故障矩阵，不搭建新的测试框架；已有无关回归测试保留。每阶段先运行根 Biome 格式化，再跑类型检查和相关测试；最终全包离线测试、构建及独立审查。

## Out of Scope

- 不安装、重启或操作用户真实 daemon。
- 不开放修改项目 cwd，不改变解绑导致会话重建的现有行为，不保证解绑不中断 Pi。
- 不引入账号数据库、跨文件事务、可靠通知队列、文件监听、后台扫描、清理服务或复杂生命周期状态机。
- 不新增 name 入索引的数据迁移或专用清理命令，不承诺崩溃后自动补做清理。
- 不改变微信协议、既有轮询重试策略、RPC framing、广播超时或 Pi SDK 边界。
- 不承诺配置保存即运行态同步，也不承诺清理警告意味着敏感文件已经消失。

## Further Notes

- 用户已确认：CLI 写全部控制配置，daemon 只读控制配置并维护运行态；管理操作可串行；离线允许保存待应用；无法确认停止则不清文件；在线应用失败/未知非零退出但不回滚；仅清理警告不改变成功；cwd 保持固定。
- 用户已确认登录替换受绑定约束，同 ID 凭据变化需要重建 monitor；有绑定删除必须拒绝，要求先解绑。
- 本次方向替代前版的在线-only logout、daemon 写索引和保存失败恢复 monitor 方案；不要混用两套顺序。
- 先前因登录 CLI 绕过 daemon 写入协调而暂停；用户随后确认将全部控制配置写入统一到 CLI。本轮已完成实现，采用 Linux util-linux flock 和本地文件系统，升级前需停止不参与锁的旧 daemon。
- 验证：类型检查、Biome、构建和 pack 通过；31 个离线测试文件、248 项测试通过。cwd 删除重建回归先红后绿，独立审查确认阻塞项已关闭；未操作真实微信、模型或凭据。
- 独立非阻塞后续：Issue #43（项目列表错误详情）、#44（API 元数据版本识别）、#45（发布文档 allowlist）。
- 用户要求轻量实现与核心测试；未选定的锁库、串行入口或应用结果表示方式由实施选择，不因此扩展为通用事务框架。
- 实施遇阻塞暂停，独立非阻塞问题另建 issue，不顺手扩大范围。
